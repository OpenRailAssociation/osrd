# Diesel to SeaORM migration plan

Status: planning  
Last updated: 2026-08-19

## Objective

Replace Diesel in Editoast with SeaORM 2 and SQLx while preserving application behavior and keeping the migration reviewable.

The migration has three distinct concerns:

1. replace Diesel migrations with SQLx SQL-file migrations;
2. replace the database pool and test-database infrastructure with an asynchronous `Db` wrapper around SeaORM;
3. replace Diesel DSL, raw Diesel SQL, and the custom `Model` abstraction with module-qualified SeaORM entities and checked SQLx queries.

The first implementation is intentionally conservative. It should preserve existing SQL, public serialization, errors, ordering, pagination, transaction behavior, and batching wherever practical. SeaORM-specific cleanup and redesign belong in later work.

## Non-negotiable constraints

- Use Jujutsu for version control.
- Never push.
- Do not squash revisions. Only the plan owner may perform the eventual squash.
- Prefix revisions with `ai: ` to distinguish them from those belonging to the plan owner.
- Rewrite and reorder revisions with Jujutsu as needed to keep each revision single-purpose, clean, and reviewable.
- Only rewrite or reorder revisions starting with `ai: `. The others are to be considered immutable.
- Keep changes mechanical and review-oriented; avoid unrelated refactors.
- Every comment, test, helper, type, feature, and configuration introduced by a revision must be part of the intended final implementation. Do not add transitional scaffolding, one-off tests, throwaway helpers, explanatory code comments for descendant breakage, or any other intermediary work.
- Each revision establishing a standalone crate must build and lint that crate. Revisions scoped to direct `src` submodules are deliberate review checkpoints in a broken root-crate stack and are validated together only in the final root-restoration revision.
- Do not add a dual Diesel/SeaORM runtime compatibility layer solely to keep descendants building.
- Do not add any compatibility work to make the intermediate `src` revisions compile.
- Do not retain the custom `models::prelude` API.
- Do not generate a replacement model prelude.
- Do not alias SeaORM types back to the old model names. Call sites must use module-qualified names such as `project::Model`, `project::Entity`, and `rolling_stock::ActiveModel`.
- The custom `editoast_derive::Model` derive must be removed completely. The rest of `editoast_derive` remains.
- The final database wrapper is named `Db`.
- `Db` and its test APIs must be asynchronous and must not call `block_on`.
- Preserve the current PostgreSQL TLS behavior. Changing certificate policy or TLS implementation behavior is out of scope.
- Use down migrations for all new SQLx migrations after the baseline. The SQLx baseline is a non-revertible simple migration with no down file.
- Check in SQLx offline query metadata, but do not add a new CI `cargo sqlx prepare --check` enforcement step in this migration.
- Necessary replacements of existing Diesel migration commands in CI are in scope; new offline-metadata CI policy is not.

## Confirmed deployment assumptions

- Every deployed database will be upgraded to the last Diesel migration before the SQLx cutover.
- Partially migrated Diesel databases do not need to be supported.
- Fresh databases execute the SQLx baseline normally.
- Existing databases must mark the SQLx baseline as applied without executing it, using `sqlx migrate override skip` with the baseline target version.
- The SQLx migration table is `_sqlx_migrations`; the legacy Diesel history is not used after cutover.
- Declare SeaORM as `sea-orm = "2.0"` and commit the resolved dependency graph in `Cargo.lock`.
- The SQLx library and `sqlx-cli` versions must match and be pinned deliberately.

## Target architecture

### Migrations

- Migrations remain SQL files.
- SQLx owns migration discovery, checksums, application, reversion, and migration history.
- Use SQLx reversible file names for migrations after the baseline:
  - `<version>_<description>.up.sql`
  - `<version>_<description>.down.sql`
- The SQLx baseline is a simple, non-revertible `<version>_<description>.sql` migration with no down file.
- Configure `sqlx.toml` with `migrate.defaults.migration-type = "reversible"` so the simple baseline does not cause later `sqlx migrate add` commands to infer more simple migrations.
- Embed migrations for test-database setup with `sqlx::migrate!()`.
- Add the build-script/path tracking recommended by SQLx so adding a migration retriggers compilation.
- Treat applied migration files as immutable because SQLx validates checksums.

### Database crate

`database::Db` owns a SeaORM `DatabaseConnection`, backed by a SQLx PostgreSQL pool.

Construction should follow one pool, two interfaces:

1. construct and configure a SQLx `PgPool`;
2. run SQLx migrations against that pool when setting up fresh/test databases;
3. construct SeaORM from the same pool using `SqlxPostgresConnector::from_sqlx_postgres_pool`;
4. store the resulting SeaORM `DatabaseConnection` in `Db`.

There must not be a separate application SQLx pool and SeaORM pool.

`Db` should:

- be cheaply cloneable;
- expose the SeaORM connection through a narrow, conventional API such as `AsRef<DatabaseConnection>` or a named accessor;
- allow access to the underlying PostgreSQL pool only for SQLx checked queries, migrations, and low-level operations;
- provide async construction for production and tests;
- provide database ping/health behavior without manually acquiring a connection;
- contain only the extra state required for test-database ownership and cleanup.

The following abstractions disappear:

- `DbConnectionPoolV2`;
- `DbConnection`;
- connection `RwLock` wrappers;
- handler-level `get()` and `get_ok()` calls;
- `iter_conn`;
- Diesel migration harnesses;
- the deadpool Diesel pool.

### Test databases

Preserve isolated, per-test databases and the pre-migrated template optimization.

The simple first implementation should:

1. acquire an async process-wide guard for template creation;
2. derive the template database name from a hash of the complete ordered SQLx migration manifest—version, type, and complete bytes for every migration—plus the complete bytes of `database/sql/init_test_db.sql`;
3. create the template database and required extensions/schemas;
4. apply SQLx migrations to the template through `PgPool`;
5. clone the template for each test database;
6. construct a SQLx application pool for the clone and wrap it in SeaORM;
7. close pools before attempting database deletion;
8. perform cleanup asynchronously, without `block_on` or a busy waiting loop.

The test API remains `Db::for_tests().await`; do not expose a public close or cleanup method. `Db` is internally reference counted, test-database ownership is held by the shared inner state, and dropping the final clone schedules cleanup exactly once. Cleanup must not depend on the lifetime of the test's Tokio runtime: use an internal long-lived asynchronous cleanup worker or an equivalent drop-driven mechanism covered by lifecycle stress tests. Do not redesign the rest of the testing framework.

### Models

Entities live in the `models` crate and are organized by module:

- `project::Model`
- `project::Entity`
- `project::ActiveModel`
- `project::Column` or SeaORM 2 typed column constants

There is no `models::prelude`, generated prelude, compatibility alias, or custom generic CRUD trait.

Use generated SeaORM entities as a starting point, then curate them for:

- serde and OpenAPI derives;
- existing field names and serialization;
- primary and unique keys;
- explicit relationships, including the current manual `train_schedule_round_trips.left_id` relationship;
- custom PostgreSQL enums;
- custom Rust value wrappers;
- tables that should be excluded from entity generation.

Exclude at least:

- `spatial_ref_sys`;
- PostGIS-heavy `infra_layer_*` tables that are only used through specialized SQL;
- other extension/infrastructure objects that are not application CRUD entities.

Do not omit `train_schedule`. It must have a normal `train_schedule::Entity` and `train_schedule::Model`, even though interval fields require special handling.

### Query policy

Use the narrowest mechanism that preserves the current query:

1. SeaORM entity CRUD and query builder for straightforward model operations;
2. SQLx checked macros for static raw SQL:
   - `query!`;
   - `query_as!`;
   - `query_file!`;
   - `query_file_as!`;
3. runtime SQLx or SeaORM statements for genuinely dynamic SQL that cannot be expressed as a literal.

SeaORM `raw_sql!` is not a substitute for SQLx compile-time checking. It may still be used where its expansion features are useful and compile-time database validation is not possible.

For dynamic queries:

- bind all values;
- allowlist dynamic identifiers;
- keep table/column selection typed where possible;
- preserve or add focused integration tests because macros cannot validate the final SQL;
- avoid opportunistic query rewrites.

### Transactions

- A transaction belongs entirely to one query stack. Mixing SeaORM and SQLx queries in the same transaction is out of scope.
- Use SeaORM `DatabaseTransaction` for transaction families expressed through SeaORM entities, query builders, and SeaORM statements.
- Use a SQLx transaction only when the whole transaction family is implemented through SQLx.
- A static raw query inside a SeaORM transaction must execute as a SeaORM statement on that `DatabaseTransaction`; compile-time SQLx checking is deliberately waived for that query and replaced with a focused integration/rollback test.
- Let model/helper functions accept the owning stack's database or transaction executor where this reduces duplication.
- Transaction boundaries may be rearranged when it makes the diff easier to review, provided externally observable behavior and atomicity are preserved.
- Never reach back to `Db` or its pool from inside a transaction callback; doing so would acquire a different connection.
- Do not introduce a project-specific connection wrapper to mimic `DbConnection`.

## Custom value-type strategy

Custom value types replace the field transformations previously generated by `editoast_derive::Model`. They are ordinary, explicit SeaORM/SQLx types rather than a new ORM abstraction.

### Unit quantities

The current quantities are external UOM types, so SeaORM traits cannot be implemented on them directly because of orphan rules.

Use small local wrappers backed by the actual database representation, for example:

- meter backed by `f64`;
- meters per second backed by `f64`;
- acceleration backed by `f64`;
- kilograms backed by `f64`;
- seconds backed by `f64`;
- millisecond offsets backed by `i64`.

Each wrapper should:

- derive or implement SeaORM `ValueType`, `TryGetable`, `Nullable`, and value conversion;
- convert to and from the corresponding UOM quantity;
- preserve existing serde and OpenAPI representations;
- provide only small conversion/accessor conveniences, not generic model behavior.

Use primitive-backed local wrappers and keep UOM quantities at the conversion boundary.

### JSON fields

Prefer a local transparent JSON wrapper using SeaORM JSON support and `TryGetableFromJson`, with explicit SQLx `Json<T>` use in checked raw queries.

Use a generic transparent wrapper and keep its trait bounds no broader than the affected fields require.

### String and remote fields

- `Tags` is already a local newtype and should become an ordinary PostgreSQL-array value type.
- Local validated string/domain types should use a transparent scalar wrapper or explicit conversion.
- Do not add SeaORM dependencies to `schemas` merely to make foreign schema types database-aware.

### Integer-backed Rust enums

The current macro stores several Rust enums as `SMALLINT`.

Use a small local numeric adapter or concrete numeric enum wrappers that:

- encode through `i16`;
- validate decoding;
- preserve the existing JSON/OpenAPI enum shape;
- avoid repeating CRUD behavior.

Use a small local numeric adapter, with concrete wrappers only where a field needs distinct validation or API conversion.

### PostgreSQL enums

`timetable_type` and `train_main_category` are real PostgreSQL enum types.

- Model them as local SeaORM `ActiveEnum`s.
- Mirror the database variant names exactly.
- Add explicit conversions to and from the corresponding `schemas` enums.
- Implement/derive SQLx type support when checked raw queries use them.
- Test scalar, optional scalar, and array round trips.

### Arrays whose PostgreSQL elements may be null

PostgreSQL array types permit null elements even though application models generally expose `Vec<T>`. The existing `non_null_array` transformation silently discards null elements.

Preserve that behavior at the Rust decoding boundary; do not normalize deployed data as part of this migration.

Use a reusable local wrapper, conceptually `NonNullArray<T>(Vec<T>)`, with these semantics:

- reads decode the database value as `Vec<Option<T>>` and flatten it;
- writes encode only `Vec<T>`, so application writes never create null elements;
- serde exposes the ordinary `Vec<T>` representation;
- conversion and dereference/accessor behavior remain small and explicit;
- the implementation delegates to SeaORM's PostgreSQL-array value support and, where needed, SQLx decoding through the underlying PostgreSQL row.

Attempt one generic implementation with constrained bounds. If SeaORM's derives or enum-array support make that disproportionate, generate a few concrete wrappers for strings, IDs, and `TrainMainCategory` instead.

Use a plain `Vec<T>` for arrays that do not currently need null-flattening semantics. Add round-trip tests that include an explicit null element for wrappers that do.

### PostgreSQL intervals

There are two unrelated `PgInterval` types:

- `sea_query::table::PgInterval` describes column qualifiers such as `YEAR`, `DAY TO SECOND`, and `HOUR`; it is schema metadata and carries no duration value;
- `sqlx::postgres::types::PgInterval` is the runtime value containing months, days, and microseconds.

`train_schedule::Entity` remains mandatory.

Implement a local model value type that preserves the existing `chrono::Duration` semantics:

1. expose `ColumnType::Interval(None, None)` as its SeaORM column type;
2. decode and encode through SQLx's runtime `PgInterval` using SeaORM's PostgreSQL row/query-result integration;
3. preserve Diesel's current decoding rule of one PostgreSQL month as 30 days;
4. use the same value type for entity reads and writes;
5. test select, insert, update, every interval filter used by the application, and SQLx checked raw queries.

Keep the entity, interval value type, and interval-specific expressions in the `train_schedule` module. Do not replace the entity with a SQLx-only model or change interval columns to integer columns in this migration.

### PostGIS geometry

SQLx support for PostgreSQL's built-in `POINT`, `LINE`, `PATH`, and related types does not cover the PostGIS extension's `geometry` type.

Do not create a generic SeaORM PostGIS geometry value type during this migration.

For existing geometry queries:

- preserve current GeoJSON-producing SQL where it already works;
- use `ST_AsBinary(geometry)` to obtain `bytea` only where a GEOS object is actually required;
- construct GEOS geometry with `geos::Geometry::new_from_wkb`;
- carry or set SRID explicitly because ordinary WKB does not preserve it;
- for necessary writes, bind WKB as `bytea` and use `ST_GeomFromWKB(..., srid)`;
- keep geometry conversion inside the owning model, `generated_data`, or map query module.

Geometry-heavy layer tables remain raw-query boundaries and are excluded from generated entities.

## Behavior that must be preserved

### Public and error behavior

- JSON and API representations;
- OpenAPI schemas;
- not-found behavior and `*_or_fail` semantics;
- unique, check, and foreign-key violation mapping;
- constraint names and useful column/value details where currently exposed;
- missing-ID reporting from batch operations;
- default ordering;
- list, count, and list-and-count semantics;
- externally visible transaction/atomicity behavior.

SeaORM's broad `DbErr` categories are not sufficient for all existing errors. Inspect the underlying SQLx/PostgreSQL database error and preserve SQLSTATE, constraint, column, and detail parsing where the current HTTP error contract depends on it.

### CRUD semantics

For every custom `Model` operation being removed, record its direct replacement in the owning module's review notes:

| Existing behavior | Initial replacement |
| --- | --- |
| `retrieve` / `retrieve_or_fail` | `Entity::find_by_id` or explicit unique-key filters plus `.one()` |
| alternative/composite identifier | explicit typed filters over all identifier columns |
| `exists` | minimal select/count/existence query |
| changeset builder | SeaORM `ActiveModel` builder or explicit `Set`/`NotSet` fields |
| create / create batch | `ActiveModel::insert` / `Entity::insert_many` with preserved chunking |
| update / save | loaded `ActiveModel` update or explicit update query preserving identifier semantics |
| delete variants | entity delete or filtered delete with affected-row interpretation |
| list / count | SeaORM select/paginator while preserving filters, order, and count scope |
| batch missing IDs | query returned IDs and compute the same missing set explicitly |

Do not add a new generic trait reproducing the old table.

### Pagination

Preserve current pagination ordering and behavior first, including the existing primary-key offset optimization where callers depend on it. Add regression tests for custom ordering before translating it. Any switch to conventional SeaORM pagination is follow-up work.

### Batch limits

The custom model layer currently chunks operations and protects the PostgreSQL bind-parameter limit. SeaORM and SQLx are subject to the same server limit.

- retain explicit chunking for large batch operations;
- derive a safe chunk size from fields/binds where practical;
- preserve empty-batch behavior;
- test at least one large create, retrieve, update, and delete batch.

### Observability

Replace the current custom Diesel query tracing with SeaORM's simplest documented logging path:

- enable SeaORM's `debug-print` feature and feed its events into the existing `tracing` subscriber, following [SeaORM's debug-log guidance](https://www.sea-ql.org/SeaORM/docs/install-and-config/debug-log/);
- interpolated bind values are allowed in logs;
- disable SQLx statement logging to avoid duplicate query events;
- do not recreate the Diesel tracing wrappers, spans, helpers, or attributes;
- document the intentional observability change in the final operational documentation.

## Revision plan

The descriptions below are intended revision boundaries, not commands to execute. Every revision contributes only final implementation material. Rewrite the stack as needed to preserve these boundaries, never push, and leave all squashing to the plan owner.

### Revision 1 — produce the final SQLx baseline

Goal: derive and review the final non-revertible SQLx baseline while leaving the active Diesel migration stack unchanged until the cutover revision.

Work:

- Resolve the actual latest Diesel migration version at implementation time.
- Create a fresh PostgreSQL database with the existing full migration history.
- Generate a clean schema baseline from that database rather than concatenating historical up files.
- Audit and include required seed/reference data separately.
- Preserve extensions and external initialization assumptions from `database/sql/init_test_db.sql` and deployment initialization.
- Audit functions, triggers, enums, sequences/identity behavior, indexes, constraints, views/materialized views, grants, and comments.
- Choose a valid numeric SQLx version that represents the already-applied latest Diesel state.
- Add the complete baseline once, at its final path and with its final simple SQLx `<version>_<description>.sql` filename.
- Leave the existing Diesel migration directories and active migration runner unchanged in this revision.
- Do not create a Diesel `up.sql`/`down.sql` wrapper, compatibility helper, or transitional comment around the baseline.

Validation:

- create one database from the old migration stack and one from the baseline;
- compare normalized `pg_dump --schema-only` output;
- compare catalog inventories for extensions, enum values/order, functions, triggers, constraints, indexes, sequences, and views;
- compare required reference data;
- execute the final baseline SQL against a fresh initialized database;
- verify the existing Diesel migration stack remains unchanged and still reaches the comparison schema;
- build/lint `database` and `models` and run their relevant database tests.

Review focus:

- the baseline should describe the final schema, not replay historical states;
- every included data statement must have an explicit reason;
- the baseline file is already in its final SQLx form and will not be moved or rewritten by the cutover revision.

Goal: make SQLx the only migration system.

Work:

- Add pinned SQLx migration dependencies and a matching pinned `sqlx-cli` installation path.
- Remove the historical Diesel migration directories and activate the existing final simple SQLx baseline without moving or rewriting it.
- Configure the migration directory consistently for the CLI and `sqlx::migrate!()`.
- Set `migrate.defaults.migration-type = "reversible"` in `sqlx.toml`; do not rely on type inference from the simple baseline.
- Add migration path build-script tracking.
- Replace Diesel migration commands in:
  - `justfile`;
  - `Dockerfile`;
  - Docker Compose and PR-test Compose files;
  - `process-compose.yaml`;
  - Nix/flake development tooling;
  - Helm/chart init commands and documentation;
  - database cleanup/helper scripts;
  - Editoast README and developer instructions;
  - existing CI database initialization commands;
  - CLI messages that instruct users to run Diesel migrations.
- Remove Diesel CLI installation where it is no longer needed for migrations.
- Document the two deployment paths:
  - fresh database: `sqlx migrate run`;
  - existing fully migrated database: `sqlx migrate override skip --target-version <baseline>`, followed by normal future migration runs.
- Do not add `cargo sqlx prepare --check` to CI.

Validation:

- run the baseline on a fresh initialized database;
- use `override skip` on a clone produced by the old Diesel stack;
- verify `sqlx migrate info` reports identical installed state afterward;
- verify `sqlx.toml` explicitly configures future `sqlx migrate add` operations as reversible;
- verify that, when only the baseline remains applied, `sqlx migrate revert` reports that no migration is available to revert and leaves the baseline row installed;
- verify runtime/container images contain the intended exact SQLx CLI version;
- verify no deployment path still invokes `diesel migration`.

Review focus:

- baseline SQL is activated without being moved or rewritten;
- the SQLx baseline cannot be reverted through the normal CLI;
- the skip command is never used for fresh databases or future migrations;
- no new CI policy is introduced.

### Revision 4 — replace the database crate with `Db`

Goal: make `database` SeaORM/SQLx-native while preserving test isolation.

Work:

- Put test-database ownership in `Db`'s reference-counted inner state and schedule cleanup exactly once when the final clone is dropped; do not add a public explicit-close protocol.
- Replace string-matched database errors with PostgreSQL SQLSTATE where possible.

- Preserve database creation collision handling and backend termination before drops.
- Remove deadpool, Diesel connection instrumentation, `DbConnectionPoolV2`, `DbConnection`, manual connection acquisition, `iter_conn`, and all `block_on`/busy-wait behavior from the crate.

Validation:

- `cargo check --package database`;

- parallel isolated-test-database creation;

Expected stack state:

- `database` builds and lints;
- Diesel-dependent descendants may be broken until their own revisions;
- no compatibility connection wrapper is added to hide that breakage.

### Direct `src` submodule revisions

From this point through the `src/client` revision, each revision owns exactly one direct submodule declared by `src/main.rs`. The root `editoast` crate is expected not to compile, and no compatibility work is permitted. These revisions are review checkpoints: perform formatting, mechanical searches, SQL review, and metadata assignment locally, then run their executable validation together in the final root-restoration revision.

The current audit finds no ORM migration work in `src/authentication.rs` or `src/map.rs`. If implementation-time changes become necessary in either, add one dedicated revision for that direct submodule rather than folding the changes into another `src` revision.

## SQLx offline metadata workflow

- Generate `.sqlx` metadata from a database created from the current SQLx migrations.
- Use the same PostgreSQL extensions and enum definitions as development/test databases.
- Configure type overrides for local enums/newtypes where SQLx cannot infer the intended Rust type.
- Prefer `query_file!`/`query_file_as!` for existing SQL files so SQL remains reviewable.
- Add or update metadata in the same revision as every checked query or relevant migration change.
- When a direct `src` submodule revision cannot compile independently, generate its metadata from the fully migrated descendant/tip and assign the resulting query metadata files back to the owning revision. Do not defer ownership to the root-restoration revision.
- Add a documented local command or `just` recipe for preparation/checking.
- Ensure Docker/cargo-chef build contexts include `.sqlx` before query macros compile.
- Do not add new CI enforcement in this migration.

## Baseline and cutover runbook requirements

Before deployment, documentation must contain a concrete, copy-pasteable runbook with safeguards.

### Fresh database

1. initialize roles, extensions, and schemas using the existing deployment process;
2. run `sqlx migrate run`;
3. verify `sqlx migrate info`;
4. start Editoast and run its health check.

### Existing database

1. back up the database;
2. verify the database is at the final Diesel migration version;
3. verify the schema fingerprint/equivalence expected by the baseline;
4. run `sqlx migrate override skip --target-version <baseline-version>`;
5. verify the baseline is installed with the expected checksum;
6. run `sqlx migrate run` for any migrations after the baseline;
7. start Editoast and run health/smoke checks.

The runbook must explicitly warn that `override skip` is dangerous and invalid if used against an empty or outdated schema because it records migrations without executing them.

## Risk register

### Baseline completeness

Risk: a schema dump omits required data or external initialization assumptions.

Mitigation: old-stack/new-baseline database comparison, explicit reference-data inventory, catalog comparison, and fresh application smoke tests.

### Incorrect SQLx baselining

Risk: executing the baseline on an existing database recreates objects; skipping it on a fresh database leaves no schema.

Mitigation: separate runbooks, preflight schema/version checks, backup, and `sqlx migrate info` verification.

### Entity generation and PostGIS

Risk: automatic generation emits unusable geometry fields or extension tables.

Mitigation: explicit exclusion list, curated entities, and raw SQL geometry boundaries.

### Interval binding

Risk: SeaORM can describe and decode an interval column but the selected SeaQuery version cannot bind a runtime interval value.

Mitigation: retain `train_schedule::Entity`, reproduce the existing month-to-duration rule in the local value type, and cover interval reads, writes, and filters with database round-trip tests.

### Nullable array elements

Risk: decoding a PostgreSQL array containing a null into `Vec<T>` fails or changes current flattening behavior.

Mitigation: `NonNullArray` decoding wrapper, explicit null-element test, and non-null application writes.

### Error response drift

Risk: SeaORM collapses constraint errors and changes HTTP responses.

Mitigation: inspect underlying PostgreSQL errors and maintain parity tests for unique/check/foreign-key violations.

### Pagination/order drift

Risk: replacing the custom list implementation changes ordering, offsets, or counts.

Mitigation: freeze representative results in tests and preserve current implementation semantics before later optimization.

### Bind parameter limits

Risk: large SeaORM batch inserts/updates exceed PostgreSQL's parameter limit.

Mitigation: preserve explicit chunking and test boundary-sized batches.

### Transaction drift

Risk: nested calls run outside the intended transaction after connection-wrapper removal.

Mitigation: keep every transaction on exactly one query stack, never reacquire from `Db` inside a transaction, and add rollback tests around multi-step operations.

### Test database leaks

Risk: pools remain alive when cloned databases are dropped.

Mitigation: reference-counted ownership, exactly-once drop-driven cleanup on the final clone, an internal cleanup worker independent of the creating Tokio runtime, termination fallback, and parallel teardown tests. Destructors do not run after every abrupt process termination, so document stale prefixed-database discovery and operator cleanup as the recovery path; do not claim `Drop` covers process abort or kill.

### Dynamic SQL

Risk: dynamic query families lose Diesel's typed fragments without gaining SQLx macro checking.

Mitigation: identifier allowlists, bound values, family-level integration tests, and SQL logging in tests.

### Performance regression

Risk: equivalent-looking ORM queries generate different joins, projections, counts, or round trips.

Mitigation: inspect generated SQL, compare query plans for hot paths, and keep current raw SQL for complex paths during the first migration.

### Tracing regression

Risk: pool/query metrics or spans disappear, or SeaORM and SQLx emit duplicate query events.

Mitigation: enable SeaORM `debug-print` through the existing `tracing` subscriber, allow its interpolated bind values, disable duplicate SQLx statement logging, and do not recreate custom Diesel tracing infrastructure.

### Intra-crate broken stack

Risk: separate review revisions for root modules cannot each build the entire `editoast` crate after the custom model API is removed.

Mitigation: document expected breakage per revision, prohibit compatibility work, keep one revision per changed direct `src` submodule, and validate all of them in the final root-restoration revision.

## Definition of done

The migration is complete when:

- SQLx is the only PostgreSQL migration runner;
- fresh databases run the baseline and existing current databases can safely skip it;
- the SQLx baseline is a simple migration with no down file and cannot be reverted through the normal CLI;
- all future migrations have up/down SQL files;
- `sqlx migrate add` defaults to reversible migrations despite the simple baseline;
- `database::Db` is asynchronous and wraps SeaORM over the same SQLx pool used for migrations/checked queries;
- test databases remain isolated and reliable without `block_on`;
- application entities are module-qualified SeaORM entities with no aliases or model prelude;
- `train_schedule::Entity` exists and interval behavior is covered by round-trip tests;
- geometry-layer tables remain explicit raw-query boundaries;
- eligible static SQL is compile-checked by SQLx with checked-in offline metadata;
- each checked query's offline metadata is owned by the same revision as the query;
- dynamic SQL is allowlisted/bound/tested;
- the custom `Model` derive and custom prelude are gone;
- Diesel, diesel-async, diesel-migrations, deadpool Diesel, schema files, and Diesel CLI tooling have no remaining consumers;
- external API, error, ordering, pagination, batch, and transaction parity tests pass;
- no transaction mixes SeaORM and SQLx execution;
- `database`, `models`, and root `editoast` build and lint;
- no new offline-metadata CI enforcement has been added;
- no transitional or throwaway comments, tests, helpers, types, features, or configuration remain;
- revisions have been rewritten as needed to keep the stack clean and reviewable;
- no revision has been squashed by anyone other than the plan owner;
- no push has been performed.
